# 产物规范模块

> **模块定位**：定义全流程产物文件的格式规范，所有阶段（S1-S6）共用。本模块只定义"格式"（字段、模板、命名规则），不定义"逻辑"（何时执行、如何循环）。执行逻辑由 `流程控制规范.md` 定义。

> **与横切机制的边界**：横切机制.md 机制2（产物索引闭环）只保留概述+引用"详见产物规范.md"。本模块是产物格式相关的唯一真实来源。

## 一、产物目录结构

每个阶段有独立的产物目录：

```
项目根目录/
├── S1_步骤产物/      # S1 题目理解与初稿方案

├── S5_步骤产物/      # S5 综合校验
└── S6_步骤产物/      # S6 组装与定稿
```

## 一.5 支撑材料目录标准（单一真相源）

> 本目录标准是支撑材料打包的**唯一锚点**——S3 写代码、S4 步骤7、S6 打包三处都引用本节，禁止各自描述另一套结构。

```
支撑材料根目录（= S3_步骤产物/ 目录本身）
├── 代码/
│   ├── config.py            ← 路径基准唯一真相源
│   ├── 问题一_求解.py        ← 独立脚本，可单独跑
│   ├── 问题一_验证.py
│   ├── 问题二_求解.py
│   ├── 问题二_验证.py
│   ├── 数据/                ← 清洗后数据 + 原始数据
│   └── requirements.txt
├── 图片/                    ← 问题一/、问题二/ 子目录
├── 表格/
└── 一键运行.bat（可选）
```

**核心铁律**：打包 = 原样复制压缩，不重组、不改名、不移动。代码目录长什么样，支撑材料里就长什么样。

**路径基准（config.py）**：代码内所有路径一律经 `config.py` 统一解析，禁止各写各的 `../` 相对路径：

```python
import os
BASE_DIR = os.path.dirname(os.path.abspath(__file__))   # = 代码/，与 cwd 无关
DATA_DIR = os.path.join(BASE_DIR, '数据')
RESULT_DIR = os.path.join(BASE_DIR, os.pardir, '表格')
FIG_DIR = os.path.join(BASE_DIR, os.pardir, '图片')
LOG_DIR = os.path.join(BASE_DIR, os.pardir, '中间数据')
```

## 二、产物文件命名规范

### 2.1 基本格式

```
步骤{步骤号}_{产物名称}.md
```

- 步骤号：阿拉伯数字，如 `步骤1`、`步骤2-2`
- 产物名称：中文，简洁明了，如 `题目理解`、`建模计划`
- 完整示例：`步骤1_题目理解.md`

### 2.2 带版本号的命名（迭代产物）

循环迭代中的产物需要带版本号：

```
步骤{步骤号}_{产物名称}_v{版本号}.md
```

- 版本号从 v1 开始，每次迭代递增
- 示例：`步骤2-2_建模计划_v1.md`、`步骤2-2_建模计划_v2.md`
- 多问题场景：`问题{X}_步骤{步骤号}_{产物名称}_v{版本号}.md`

### 2.3 代码类与支撑材料新产物命名（v3.1 新增）

代码类产物不遵循 `.md` 命名，采用以下固定命名（与 `一.5 支撑材料目录标准` 一致，S3/S4/S6 三处统一引用）：

| 产物 | 固定名称 | 位置 | 说明 |
|------|----------|------|------|
| 路径基准 | `config.py` | `代码/` | 路径基准唯一真相源，所有脚本统一 import |
| 问题求解脚本 | `问题X_求解.py` | `代码/` | 独立脚本，可单独跑（`python 问题X_求解.py`） |
| 问题验证脚本 | `问题X_验证.py` | `代码/` | 独立验证脚本 |
| 依赖清单 | `requirements.txt` | `代码/` | 版本固定 |
| 冒烟运行日志 | `冒烟运行.log` | 打包后根目录 | 拿成品包真实跑一遍的日志 |
| 模型验证结论 | `模型验证结论.md` | `S3_步骤产物/` | 步骤3-5.5 产出（四检+可回溯+三项检验） |
| 开发日志 | `开发日志.md` | `S3_步骤产物/` | **可选辅助**（非强制产物，老公需要时记录改动/耗时/报错） |

### 2.4 AI 使用记录

每个阶段收尾产出一份 AI 使用记录：

```
AI使用记录.md
```

S4 拆分为 A/B/C 三份：`AI使用记录A.md`、`AI使用记录B.md`、`AI使用记录C.md`

### 2.5 全流程产物清单

| 阶段 | 步骤产物数 | AI记录 | 合计 | 版本化产物 |
|------|-----------|--------|------|-----------|
| S1 | 6 | 1 | 7 | 无 |
| S2 | 3 | 1 | 4 | 步骤2-2 建模计划（vN迭代） |
| S3 | 每问题5+全局4 | 1 | 视问题数 | 步骤3-1至3-4（vN迭代） |
| S4 | 13 | 3(A/B/C) | 16 | 无 |
| S5 | 3 | 1 | 4 | 无 |
| S6 | 3 | 1 | 4 | 无 |

> S3 全局产物：数据清理.log + 结果摘要.md + 变量符号约定.md + 模型验证结论.md（步骤3-5.5 新增）。开发日志.md 为可选辅助，不计入强制产物。
> 添加新阶段或新步骤时，在此表中增加一行/一列即可，产物索引检查.py 同步更新。

### 2.6 上下文衔接落盘格式（关键点层，每步产物强制包含）

每个步骤产物文件**开头**（`## 变更说明` 之前）必须包含 `【上下文衔接】` 字段，解决"前面干了什么 + 后面该干什么"：

```markdown
【上下文衔接】
- 前面关键点：上一步干了什么 + 结果文件路径 + 关键数值/结论
- 下一步入口：下一步该干什么 + 读哪个文件哪章
```

**落盘规则**：
- 每步产物写入时同步写入该字段，内容来自上一步产物 + `references/索引导航.md` 路由表。
- 压缩后恢复流程时：先读索引导航.md 定位当前阶段 → 读最近产物 MD 的【上下文衔接】→ 从"下一步入口"指定的文件章节继续。
- 该字段不替代产物正文，仅作流程导航；产物正文规则仍以对应阶段文件为准。

## 三、变更说明格式

### 3.1 必须包含

每个步骤产物文件**开头**必须包含 `## 变更说明` 字段：

```markdown
## 变更说明

- **版本**：v1.0（首次产出）/ v1.1（修改后）
- **与上一版本差异**：
  - 修改了 XXX 段落（原因：XXX）
  - 新增了 XXX 内容（原因：XXX）
  - 删除了 XXX 内容（原因：XXX）
- **变更时间**：YYYY-MM-DD HH:MM
```

### 3.2 版本号规则

| 版本号 | 含义 | 触发条件 |
|--------|------|----------|
| v1.0 | 首次产出 | 步骤首次完成 |
| v1.1 | 小修改 | 微循环修改中发现问题并修改 |
| v1.2 | 再次小修改 | 微循环再次修改 |
| v2.0 | 大改/迭代 | S2↔S3 循环回退后重新产出 |

> 微循环内的小修改递增小版本号（v1.1→v1.2→v1.3），循环回退后的大改递增大版本号（v1.3→v2.0）。

> ⚠️ **版本号铁律（杜绝"检查走过场"）**：微循环中每次修改产物必须递增版本号。如果所有产物的版本号都是 v1.0（零修改），说明检查走过场，需重新执行独立检查。正常情况下，至少应有部分产物经过1-2轮微循环修改（v1.0→v1.1 或 v1.0→v1.1→v1.2）。版本号递增体现在产物文件名和内容的变更说明中。

## 四、读取验证格式

### 4.1 必须包含

每一步骤开始前，AI 必须先执行读取验证，输出以下格式：

```markdown
【读取验证】
- 已读取文件：<列出所有已读取的文件名>
- 关键信息摘要：<用3-5句话概括上一步的核心结果，包括关键结论、数值、决策等>
- 与当前步骤的关联：<说明上一步结果如何指导当前步骤>
```

### 4.2 验证要求

1. 摘要中**必须包含具体数值或结论**，不能只说"已读取"或"了解内容"
2. 只有输出了读取验证摘要，才能开始当前步骤的实际工作
3. 首步骤（如 S1 步骤1）无前置产物时，读取验证改为"本步骤为全流程首步，无前置产物"

## 六、结果摘要格式

### 6.1 结果登记字段

结果摘要时（S2 步骤2-3 + S3 步骤3-5），产物文件中必须包含 `## 结果登记` 字段：

```markdown
## 结果登记

- **锁定对象**：建模计划（本文件）+ 代码结果数据（S3产物）
- **结果载体**：步骤3-5结果登记
- **结果数据清单**：步骤3-3阶段B全量运行结果中的全部数值
- **锁定时间**：YYYY-MM-DD HH:MM（用户确认锁定的时间）
- **锁定后约束**：后续 S4/S5/S6 只能引用不能修改；S4引用统一指向S3运行结果，禁止绕过S3运行结果直接引用3-3/3-5产物；S5校验基准为S3运行结果中的结果数据
- **解锁条件**：<记录什么情况下需要解锁>
- **抽样运行记录**（如发生抽样运行时填写）：
  - 抽样原因：全量运行预估时间>X小时，优化后仍>4小时
  - 采样策略：分层比例采样（分层列/采样比例/每层行数）
  - 采样比例：X%
  - 结果验证方式：与小数据手算结果的交叉验证结论
  - 论文表述建议："由于计算资源限制，采用分层比例采样，采样比例为X%"
```

### 6.2 锁定时机

| 锁定对象 | 锁定步骤 | 触发条件 |
|----------|----------|----------|
| 建模计划 | S2 步骤2-3 | 用户确认锁定 |
| 代码结果数据 | S3 步骤3-5 | 自检验算通过+用户确认 |

### 6.3 锁定后约束

1. 后续 S4/S5/S6 **只能引用**已确认的数据和计划，**不能修改**
2. 若发现不一致，不得自行修改，须按修改流程报告并等待用户确认
3. 正文数值必须来自已确认的代码运行输出，严禁手算编造
4. **S4 引用规则**：S4 写作时所有数据引用统一指向S3运行结果，禁止绕过代码实际输出直接编造数值
5. **S5 校验基准**：S5 校验以S3运行结果中的结果数据为基准

### 6.4 修改流程

```
发现需要修改已结果数据
  ↓
报告用户（说明原因+影响范围）
  ↓
用户确认解锁
  ↓
改代码/改计划
  ↓
重新验证（运行前+运行后）
  ↓
重新自检验算
  ↓
重新锁定（更新结果登记）
```

> 修改流程的执行逻辑详见 `流程控制规范.md`。本模块只定义结果登记的格式和约束。

## 七、隔离检查规范（不产出隔离检查结论）

### 7.1 检查流程

AI 将产物写入文件后，必须执行独立检查（重新读取→检查→反馈结论），**不产出独立的 `` 隔离检查反馈**。隔离子Agent直接将检查结论反馈给产者，由产者根据反馈修改产物。

**检查流程**：
1. 主AI初检（快速筛查，辅助参考）
2. spawn 隔离子Agent做终审（硬性门禁，每步必做）
3. 比对结论，以隔离子Agent为准
4. 有问题 → 微循环修改 → 重spawn检查 → 收敛
5. 没问题 → 通过，进入暂停

### 7.2 检查标准

三层检查标准（通用+分类+专属）详见 `检查模板库.md`，本模块只定义检查的执行规范。

### 7.3 五条铁律（强制执行）

1. **必须重新读取**：检查前必须用Read工具重新读取产物文件，禁止使用产出时的上下文
2. **必须有证据**：每项检查的"通过"判定必须附具体证据（引用产物中的具体段落、数值、结论），禁止只写"通过"二字，也禁止空泛证据
3. **必须递增版本号**：微循环中每次修改产物必须递增版本号（v1.0→v1.1→v1.2）
4. **必须由隔离子Agent做终审**：每次全新 spawn，不复用产者上下文，结论以隔离子Agent为准
5. **必须给出优化建议（且含升级型建议）**：即使结论为✅通过也必须给出至少1条具体优化建议，且其中≥1条必须是升级型建议——指向方案要素（模型/算法/方法/参数/验证/结构/权重等）的升级动作（改用/引入/替代/敏感性/鲁棒/消融/交叉验证/参数寻优/多目标等）。零问题必须附具体理由，禁止只写"无"

### 7.3.1 三必查板块（强制必填）

隔离子Agent检查必须覆盖三大板块（板块A 原题对齐 / 板块B 数据核查 / 板块C 优化建议）。每项必须二选一（发现/排除），禁止空话。

| 板块 | 检查项 |
|------|--------|
| 板块A 原题对齐 | 文本毛病（错别字/病句/歧义/冗余/称谓不一） |
| 板块A 原题对齐 | 逻辑毛病（断链/跳步/前提缺失/推不出结论） |
| 板块A 原题对齐 | 与原题对不对得上（逐问对照赛题） |
| 板块B 数据核查 | 数值/图表/结论是否可追溯（原始数据/代码运行/文献） |
| 板块B 数据核查 | 数据间一致性（与结果数据/编号/前后文/单位量级口径） |
| 板块B 数据核查 | 全量复算（每个可计算数值给出复算记录） |
| 板块C 优化建议 | 哪里没写清/能更严谨/更简练/可补证据文献 |

### 7.3.2 零修改直通三条件（治"每次直接通过"）

产物以 v1.0 不带修改直接通过，须**同时**满足：①三必查板块逐项给出实质排除理由（无空话）；②隔离子Agent复核通过；③阶段AI使用记录如实说明"经严格证否确无需修改"。三条缺一，必须以 v1.1 及以上走修改迭代。详见 `流程控制规范.md` 5.2.1。

### 7.3.3 独立抽查（兜底人证）

每阶段抽检 ≥30% 产物（最低 1 个）交**零作者上下文的独立会话**（只给文件路径+检查清单，不给"我想表达什么"）。独立会话发现而作者微循环没记录 → 判定"检查走过场"，该阶段其他产物一并存疑、抽检返工。
> 当作者全部声称 v1.0 直接通过且零修改时，独立抽查为**必做**（此时高可疑）。

### 7.4 隔离子Agent终审（主流程，硬性门禁）

全部产物必须由**隔离子Agent**做终审——每次全新 spawn（通过 Agent 工具，subagent_type="general_purpose_task"），**不能复用产者上下文**。

- 隔离检查者**审查范围白名单**：本轮产物文件 + 原题/赛题原文 + 允许的外部权威核查资料；**禁读**产者的思路/中间思考/建模解释、内部检查模板库。否则污染回潮 → 判定冷读不净。
- 隔离检查者每次检查都用**全新上下文**（杜绝跨轮累积污染）。
- 主AI先做初检（快速筛查，辅助参考）；**最终由隔离子Agent做终审**（独立产出问题清单+优化建议+【独立判决】，非仅复核结论）
- 隔离子Agent结论为终审结论。初检与终审不一致 → 以隔离子Agent为准
- **隔离检查者发现问题而主AI初检未发现 → 判定"初检走过场"，强制返工重查**
- **隔离检查者必须以"评委+国一"视角冷读**：显式代入评委最可能追问的问题，并对非纯元数据产物给出机理闭环判定。此机制治"自我审查视角盲区"（知识诅咒）
- 可选增益：spawn 隔离检查者时经 `model` 覆盖配置**异模型** → 真"第二颗不同大脑"

### 7.5 不通过处理

- 任一项不通过 → 进入微循环修改（修改→重新读取→spawn全新隔离子Agent→新一轮检查）
- 具体流程详见 `流程控制规范.md` 第五章

## 八、扩展指南

### 添加新产物类型

1. 确定产物名称和所属阶段
2. 按"命名规范"确定文件名格式
3. 在"全流程产物清单"表中增加条目
4. 在 `产物索引检查.py` 的 `YINGYOU_WENJIAN` 中增加文件名

### 修改产物格式

1. 找到本模块中对应的格式定义
2. 修改格式规范
3. 所有阶段的产物自动适用新格式
