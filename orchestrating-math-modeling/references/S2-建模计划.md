## 流程摘要（每步强制执行的通用流程）

> 详细规则以 `references/流程控制规范.md` 为准（第二章 9 动作序列、第三章 暂停确认、第五章 微循环修改）。以下为每步执行的流程摘要，standard（手动）与 auto 模式均强制执行，不跳过。

### 每步 9 动作序列

1. **读取验证**：读取上一步产物 + 输出三要素摘要
2. **执行**：按步骤内容产出
3. **写入MD**：产物写入独立MD文件（含 `## 变更说明`），版本号 v1.0
4. **独立检查**（审查方物理隔离，硬性门禁）：主AI重读产物做初检（辅助参考）→ **spawn 隔离子Agent做终审**（Agent工具，subagent_type="general_purpose_task"，每次全新spawn，不复用产者上下文，审查范围白名单冷读，按三层标准逐项检查并给出具体证据）→ 隔离子Agent直接返回检查结论（【独立判决】+ 问题清单 + 优化建议），不产出独立隔离检查结论文件（含 `<!-- 由隔离检查Agent直写，未经生产转述 -->` 签名 + 【独立判决】）→ 结论不一致以隔离子Agent为准
5. **问题判定**：有问题 → 修改（版本递增 v1.0→v1.1）→ 再检查 → 收敛判定；无问题 → 通过
6. **技术验证**：运行 `python scripts/阶段门禁检查.py --phase S2 --dir <项目目录>`
7. **暂停**：输出【步骤暂停 ⏸】
8. **确认**：等待用户回复"继续"
9. **进入下一步**

### 微循环技术验证 32 项（详见流程控制规范.md 5.5，以下为前16项摘要，完整32项详见原文）

1. 隔离检查结论记录存在性：每个产物 `## 变更说明` 含隔离检查结论记录
2. 重新读取确认：隔离检查结论中含 `重新读取确认` 且值为✅
3. 证据列完整性：证据列不为空、非纯"通过"二字、不命中空泛证据黑名单
4. 版本号分布：≥30%产物版本号>v1.0（产物<5时至少1个>v1.0）
5. 问题清单存在性：隔离检查结论中含 `问题清单` 段落
6. 结论字段：含 `结论` 字段且值为✅通过或❌需修改
7. 发现问题必须修改：问题清单非空但版本号仍为v1.0 → 判定"发现问题未修改"
8. 隔离子Agent复核：隔离检查结论中含隔离子Agent复核结论
9. 优化建议必填：含"优化建议"段落且至少1条实质建议（即使✅通过也必须给出）
10. 零问题附理由：问题清单为"无"时必须附具体理由，禁止只写"无"
11. 隔离子Agent独立产出：含"隔离子Agent问题清单"+"隔离子Agent优化建议"字段
12. 隔离子Agent发现而AI未发现 → 判定"检查走过场"，强制返工重查
13. 三板块A存在：隔离检查结论中含"原题对齐"板块输出，逐项证否或举证
14. 三板块B存在：隔离检查结论中含"数据核查"板块输出，逐数值追溯来源
15. 三板块C存在：含"优化建议"板块且至少1条具体定位实质建议，无"可提升"泛泛
16. 空话拦截：问题清单/证否项不得含"无/没问题/未发现问题/通过"空话而无实质证否理由

## 阶段概述

S2 是数学建模全流程的**循环"计划"环节**，与 S3（代码）构成循环关系。目标：基于 S1 产出的最终创新点初稿，经过可行性与风险分析→建模计划细化，产出可落地编程的建模计划（含公式草案、伪代码、数据流图、验收标准），送入 S3 写代码验证；验证不通过则回 S2 修正计划，循环迭代直到结果验证通过、结果摘要。

**【核心定位】**
- S2 是循环的"计划"端：产出计划 → 被 S3 验证 → 修正 → 收敛
- S3 是循环的"代码"端：写代码 → 运行前验证 → 运行 → 运行后验证
- 两者循环直到验证通过，结果数据后才进入 S4（论文写作）

**【步骤链】**
```
步骤2-1 可行性分析与风险应对（分析可行性+识别风险+升级主方案+备选方案+应对策略）
  ↓
步骤2-2 建模计划(vN) ← 循环的"计划"端
  v1: 基于步骤2-1的输出 + S1最终创新点初稿细化
  vN≥2: 基于S3验证反馈修正
  ↓ 送入S3验证
  ↑ S3不通过→回这里改计划→再送S3
步骤2-3 最终建模计划 ← 循环退出后，与代码完全一致，锁定确认
  🔒 用户确认锁定→结果摘要
（变量符号约定已移至 S3 步骤3-6，循环结束后基于最终锁定计划和代码实现整理）
```

**【与 S3 的循环关系】**

> S2↔S3循环的详细执行模式详见 `references/流程控制规范.md` 第四章。以下为简要示意：

```
【S2】建模计划(vN) → 【S3】代码实现(vN) → 【S3】运行前验证
    ├─ 不通过 → 改代码(小修,留在S3) / 改计划(大改,回S2) → 回循环
    └─ 通过 → 【S3】步骤3-3运行代码 ← 拆成两个阶段
        ├─ 阶段A：小数据运行（分层采样10%）→ 验证（语法/方向/衔接/边界/手算）
        │   ├─ 不通过 → 改代码→重跑小数据（3-3内部迭代，不写MD）
        │   └─ 通过 → 实测精估运行时间
        │       ├─ ≤4小时 → 进入阶段B
        │       └─ >4小时 → 超时处理（三级递进）
        │           ├─ 第一级：代码优化（优化后≤4h→进阶段B）
        │           ├─ 第二级：抽样运行（抽样后≤4h→进阶段B，论文诚实说明）
        │           └─ 第三级：回S2换算法（hard_blocker，如精确算法→启发式）
        └─ 阶段B：全量运行（只跑一次）→ 产出最终结果
    → 【S3】运行后验证
        ├─ ④负向 → 回S2改计划 → 再改代码 → 回循环
        ├─ ⑤不对 → 改代码(只重跑受影响问题+依赖链)/回S2改计划 → 回循环
        └─ 都通过 → 【S3】自检验算 → 【S2】最终建模计划 → ✅确认
```

**【角色】** 你是建模方案评审 + 逻辑校正专家。本阶段把 S1 的初稿方案打磨到"可落地编程"的程度，并在循环中根据代码验证结果修正计划。

- **产物目录**: `S2_步骤产物/`
- **产物清单**: 步骤2-1 + 步骤2-2（动态，可能有v3...）+ 步骤2-3 + `AI使用记录.md`（产物数动态）
- **主导技能**: `brainstorming`（SKILL_003，发散/收敛方案细节）、`modeling-paper-rubric-and-model-selector`（SKILL_004，评分维度对照、完整性校验）
- **横切支撑**: `context-memory-keeper`（SKILL_001，保持上下文连续性，记录循环迭代历史）

> 技能详细信息详见 `references/技能注册表.md`。

## 关键约束

1. `brainstorming`（SKILL_003）原生输出为结构化方案/列表，须适配为用户逐步 MD 产物格式。
2. `modeling-paper-rubric-and-model-selector`（SKILL_004）原生输出为评分 JSON，须将评分矩阵转为 MD 对照表。
3. **循环修正原则**：S3 验证不通过时，区分"小修"（改代码即可，留在S3）和"大改"（需改计划，回S2步骤2-2）。大改时须产出新版本 `步骤2-2_建模计划_v(N+1).md`，记录改动内容、原因、影响范围。
4. **as-built 优先原则**：循环退出后，步骤2-3 最终建模计划必须与代码实际实现完全一致。若计划与代码不一致，以代码为准修正计划。
5. **结果摘要机制**：步骤2-3最终确认后，结果摘要作为核心数值汇总登记，后续 S4/S5/S6 统一引用 S3运行结果（表格/ + 图片/）和结果摘要.md；如需修改，走"改代码→重新运行→重新验证→更新结果摘要"流程。详见 `references/流程控制规范.md` 第七章。
6. 变量符号约定已移至 S3 步骤3-6（循环结束后执行），基于最终锁定计划和代码实现整理符号，避免循环中计划变化导致符号不准确。
7. 决策密集：每步含决策点，发散的方案必须经 rubric 评分后交用户拍板。
8. 严禁编造公式、数据；无依据的结论标注"待补充"。
9. **题意对齐**：每步产物末尾附 `## 题意对齐校验` 段落；每步产物写入后运行 `topic_alignment_check.py` 脚本门禁（分数 < 0.6 返工）。**约束贯穿核对（U1 升级）**：建模计划须对照 S1 题目约束清单逐条核对，任何偏离题目硬性约束的方案（如题目要求"平均分流"却改用其他分流规则）必须显式论证必要性，并在题意对齐校验段落中说明。
10. **循环记录**：每轮迭代记录改动内容、原因、影响范围、排除路径，为论文"排除路径回顾"和"思考博弈感"提供素材。

### 步骤2-1 专属检查标准

| 检查重点 | 通过标准 | 检查方式 |
|----------|----------|----------|
| 假设必要性 | 每个假设都有存在的必要性（非冗余假设） | 逐条审查假设删除后模型是否受影响 |
| 假设合理性 | 假设不违背物理/数学/经济常识 | 逐条对照领域常识验证 |
| 假设可验证性 | 关键假设标注了在S3中的验证方式 | 检查每个关键假设是否有S3验证路径 |
| 与S1约束对齐 | 假设不与S1中赛题约束矛盾 | 逐条比对S1题意契约约束条件 |
| 风险识别完整性 | 实现风险/数据风险/计算风险/创新点风险均识别 | 逐类核对风险清单覆盖度 |
| 主方案升级有效性 | 升级后的主方案有效降低主要风险 | 对比升级前后风险等级变化 |
| 备选方案独立性 | 备选方案与主方案有本质区别（非小修小改） | 逐个比对备选方案与主方案的方法差异 |
| 风险-方案对应 | 每个高风险都有对应的主方案升级或备选方案 | 逐条核对高风险项的应对措施 |

### 步骤内容

直接读取 S1 选定的方法和创新点，逐一进行可行性与风险分析：

- **① 场景适配预判**：为后续"场景适配创新"做准备，识别赛题中可用于定制化建模的要素：

  | 预判维度 | 赛题要素 | 潜在适配方向 |
  |----------|----------|-------------|
  | 现实约束 | 赛题中给出了哪些现实约束条件？ | 是否需要加入约束条件建模？ |
  | 数据特征 | 数据有什么特点（噪声大/维度高/时序/缺失值多）？ | 是否需要增加预处理模块？ |
  | 工程需求 | 赛题是否有实际工程背景？ | 是否需要考虑落地性？ |
  | 多目标性 | 是否存在多个优化目标？ | 是否需要构建多层评价体系？ |

- **② 逐问可行性与风险分析**：对每个子问题的选定方法（直接引用 S1 步骤4 的方法选择），从以下维度分析可行性与风险：

  | 维度 | 检查内容 |
  |------|----------|
  | 数据可行性 | 赛题提供的数据是否足够支撑该方法？是否缺少关键数据？ |
  | 计算可行性 | 该方法的计算复杂度是否在可接受范围内？是否能在合理时间内跑出结果？ |
  | 方法可行性 | 该方法是否适用于本题的场景和约束？是否有已知的适用条件限制？ |
  | 创新可行性 | 创新点的实现难度是否可控？是否有现成的工具/库支持？ |
  | 简洁性优先 | 能用简单高效模型解决时，不强行上复杂模型（避免"杀鸡焉用牛刀"的堆砌感）；确需引入更复杂/升级模型时须有明确理由，并准备"原模型不足→新模型改进"的论证（呼应建模计划升级论证） |
  | 参数敏感性 | 模型参数对结果的影响程度如何？是否存在高敏感参数？ |
  | 数值稳定性 | 求解过程中是否存在数值不稳定的风险（如矩阵奇异、除零、溢出）？ |
  | 伪创新风险 | 是否存在过度建模/模型堆砌/难度不匹配/无优化套模板的风险？ |

- **③ 校正与升级方案**：对可行性与风险分析中发现的问题，提出校正与升级建议：
  - 哪些方法需要调整？怎么调整？
  - 哪些创新点需要降级或替换？替换为什么？
  - 哪些数据不足需要补充？如何补充？

  > **创新方向引导**：升级主方案时，优先考虑以三大创新方式作为升级方向：
  > - **模型组合创新**：是否可以组合另一个模型来弥补当前缺陷？（如单一评价→组合评价、单一预测→融合预测）
  > - **模型改良创新**：是否可以改良参数/权重/规则来消除风险？（如固定权重→动态权重、固定阈值→自适应阈值）
  > - **场景适配创新**：是否可以适配题意做定制化改造来降低风险？（如加入赛题特有约束、增加针对性预处理）

  - 升级后须重新评估风险等级：哪些风险被消除了？哪些风险降级了？哪些风险仍然存在？
  - **所有校正与升级方案均须列出可选项 + 各自优劣 + 适用条件，交由用户拍板。**
  - 用户拍板后，记录升级后的主方案，作为步骤2-2 建模计划的直接输入。

- **④ 备选方案库**：对升级后仍然存在的高风险和中风险点，设计备选方案：

  | 风险点 | 主方案（升级后） | 备选方案A | 备选方案B | 切换条件 |
  |--------|-------------------|-----------|-----------|----------|
  | <风险描述> | <升级后方法> | <备选方法> | <备选方法> | <什么情况下切换> |
  | ... | ... | ... | ... | ... |

  备选方案须注明：方法名称、适用条件、与主方案的优劣对比、切换时的数据/代码影响范围。

- **⑤ 风险应对策略**：对每个风险点，制定应对策略：
  - 预防措施：如何降低风险触发的概率
  - 应急方案：风险触发后如何应对（切换备选方案/调整参数/降级处理）
  - 监控指标：在 S3 代码阶段如何监控风险是否触发

- **⑥ 评委评分逻辑校验**：对照评委评分四维度，校验校正后方案的合理性：

  | 评分维度 | 校验内容 | 是否通过 |
  |----------|----------|----------|
  | 合理性 | 模型选择是否合理？方法是否适用于本题场景？ | ✅/❌ |
  | 优化性 | 是否有明确的优化改进（组合/改良/适配）？ | ✅/❌ |
  | 贴合度 | 模型是否贴合题意？是否考虑了赛题的实际约束和数据特征？ | ✅/❌ |
  | 完整性 | 是否覆盖所有子问题？方案是否完整？ | ✅/❌ |

  - 任一项为❌，须回③调整校正与升级方案后重新确认，直到全部通过。

- **⑦ 与循环的关系**：说明本步骤产出的升级后主方案和备选方案库将在 S2↔S3 循环中发挥作用的场景：

## 输出格式与暂停点

**【输出格式】** 一份"锁定版建模计划"：可行性与风险应对 + 逐问技术路线 + 公式 + 算法伪代码 + 数据流 + 验收标准 + 排除路径回顾。步骤2-2 可能有多轮迭代版本，最终以步骤2-3 锁定版为准。（变量符号约定在 S3 步骤3-6 执行）

### 🔴 红队审查①：Pre-mortem（方案锁定前，硬性门禁）

> **时机**：步骤2-3 锁定版建模计划完成后、用户确认锁定**之前**。这是代码还没跑、论文还没写的**最后改方案窗口**——此时改方案成本最低。

> **角色切换（关键）**：执行审查的 Agent **必须切换为"敌对评委"人格**，不是帮你完善方案，而是**要否定你的方案**。Prompt 切换：从"帮我写方案"→"如果我是要打低分的评委，这个方案哪里会崩？"

> **审查维度（逐条回答，每条须给出"判定+证据"）**：

| 攻击维度 | 审查问题 | 判定标准 |
|---|---|---|
| A. 题意对齐 | 目标函数是否严格匹配题目要求？有无"自己换了个目标"？ | 目标定义逐句比对赛题原句，偏离即判不通过 |
| B. 物理合理性 | 核心假设在真实物理下是否成立？有没有"为了好算而过度简化"导致结果失真？ | 逐条假设问"现实中真的是这样吗？"，不成立的须改或加误差说明 |
| C. 自证预言 | 是否存在"拿自己模型算出的输出当验证基准"的循环论证？ | 验证基准只能来自赛题原文/参考答案，模型输出不得当基准 |
| D. 数据匹配 | 模型与数据特点是否匹配？小样本用深度学习、因果问题用分类？ | 检查数据量/类型/质量与模型选择是否对路 |
| E. 过度设计 | 是否有"动态模型但实际≈静态"的过度设计？模型复杂度是否匹配问题难度？ | 复杂模型须证明"不可或缺"，否则判过度设计 |

> **审查流程**：
> 1. 切换为"敌对评委"人格，逐条回答上表 5 个攻击维度
> 2. 每条给出**判定（通过/不通过）+ 具体证据**
> 3. 任一维度判不通过 → **禁止锁定**，回 S2↔S3 循环修正
> 4. 全部通过 → 产出 `步骤2-3_红队审查报告.md`（含5条判定+证据），方可进入锁定确认

> **auto 模式下**：AI 自动执行红队审查，但须在决策日志中记录每条判定的理由，且**不得自我降低审查标准**。

**【步骤暂停 ⏸】** 步骤2-3 锁定确认完成后停止，请我确认锁定。**我确认锁定后，数据正式锁定，返回 S3 执行步骤3-6（统一信息中心+结果摘要）和步骤3-6（变量符号约定），完成后进入 S4（论文写作）；若我要求调整，则回 S2↔S3 循环继续迭代。**
